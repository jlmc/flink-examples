# Stateful Operators

## 1. Stateful & State

### What is a stateful application

Uma aplicação stateful mantém contexto entre eventos. Em vez de processar cada registo de forma isolada, o operador consulta e atualiza estado para produzir resultados corretos ao longo do tempo.

Sem estado, o processamento é stateless: cada evento é tratado de forma independente e não existe memória histórica para correlação temporal, detecção de padrões, acumulados ou sessões.

No domínio ADT, isto permite responder perguntas como:

- quantos eventos já chegaram por hospital;
- qual o último tipo de evento por facility;
- como evolui o fluxo de admissões/transferências/altas.

Aplicações stateful são, por isso, essenciais para:

- cálculo de métricas cumulativas em fluxos contínuos;
- regras com dependência histórica (ex.: sequência A01 -> A02 -> A03);
- janelas temporais com consistência após falhas.

### State in Apache Flink

No Flink, o estado é gerido pelo runtime e pode ser:

- local ao operador, mas consistente com checkpoints;
- recuperável após falha;
- particionado por chave (keyed state) quando usamos `keyBy`.

Detalhes técnicos relevantes (1.20.3):

- **Localidade dos dados:** o estado ativo fica no TaskManager (heap/disco local, conforme backend), evitando round-trips a sistemas externos por evento e reduzindo latência de processamento.
- **Gestão pelo runtime:** serialização, snapshots e restauração são coordenados internamente pelo motor de execução.
- **Tolerância a falhas:** checkpoints periódicos copiam snapshots consistentes para storage durável (ex.: S3/HDFS/filesystem), permitindo retomar exatamente do último ponto consistente.
- **Consistência de stream:** em conjunto com checkpoints e barreiras, o estado é restaurado de forma alinhada com a posição do fluxo.

Exemplo implementado: `stateful-and-state/StatefulAndStateAdtExample`.
