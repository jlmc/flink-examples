# 1. Time Semantics

- When dealing with a potentially unbounded stream of events that arrive continuously, time becomes a central aspect of applications.
- Let’s assume you want to compute results continuously, perhaps every hour. What would one hour actually mean in the context of our streaming application?

---

## Concept of time in Apache Flink

In distributed systems, the order in which events happen is rarely the same as the order in which they arrive for processing.
Imagine a mobile game: the player makes a move in the subway (no signal) at 10:00, but the server only receives that data at 10:05 when they leave the station.
To address this, Flink offers three main time semantics:

### 1. Event Time

It is the actual time when the event occurred in the physical world (e.g., the moment a user clicked an ad or a pressure sensor was triggered).

- **Where the time comes from**: The timestamp is embedded in the record itself (e.g., a timestamp field in JSON).
- **How time progresses**: In Event Time, progress depends on the data itself, not on system clocks.
- **Watermarks**: Event Time programs must define how to generate Event Time Watermarks, which signal time progress in the stream.
- **Advantage**: It is deterministic. If you reprocess the data tomorrow, the result will be the same, because Flink looks at the **`data clock`**, not the machine clock.
- **Result quality**: Because processing speed is decoupled from event timestamps, Event Time helps guarantee result correctness.
- **Disadvantage**: It requires additional configuration to extract timestamps and generate watermarks.
- **Challenge**: Since the internet can fail or devices can go offline (lose signal), data may arrive **out of order** or with significant **delay**.


### 2. Processing Time

It is the time measured by the wall clock of the server that is executing the operation in Flink.

- **Where the time comes from**: It is generated by the operating system of the node processing the event.
- **How windows are formed**: A processing-time window contains all events that arrive at the operator during that wall-clock interval.
- **Example**: If an application starts at 9:15 and uses hourly processing-time windows, the first window still covers 9:00-10:00 (epoch time), then 10:00-11:00, and so on.
- **Advantage**:
  - Simple to use, with no need for extra configuration.
  - Lowest possible latency, because there is no need to wait for late data or reorder anything.
  - No coordination is required between streams or machines.
- **Disadvantage**: It is not deterministic. If you reprocess the data tomorrow, the result may be different because it depends on the machine clock.
- **Challenge**:
  - It is **unpredictable**: if there is a traffic spike or a system pause (GC), the same event may fall into different time windows across different runs, leading to inconsistent results.
  - If an event arrives late, it may be processed at the wrong moment, which can lead to incorrect results, especially in window operations or joins.


### 3. Ingestion Time

Ingestion Time is the exact moment when the event enters the Flink ecosystem, that is, when it is received by the data source (Source Connector).

- **How it works**: At the moment Flink reads the record (from Kafka, a file, or a socket), it automatically assigns a timestamp based on the input server’s clock. From then on, that timestamp follows the event throughout the pipeline.
- **Advantage**:
  - It is more predictable than "Processing Time", because all operators (filtering, windows, aggregations) use the same timestamp assigned on entry. This prevents time from changing while the data travels between different machines in the cluster.
  - It handles late data better than "Processing Time", because the timestamp is fixed at ingestion and cannot be affected by later delays.
- **Where it fits**: It is a middle ground. It is more stable than Processing Time, but it does not require the developer to extract timestamps from data as in Event Time.

- **Disadvantage**:
  - It can still be affected by network delays or system failures, which may lead to inconsistent results if events arrive late or out of order.
  - It is not as robust as Event Time for handling out-of-order data, because it depends on when events are ingested, not when they actually occurred.
  - It is not recommended for cases where temporal precision is critical, such as time-series analytics or fraud detection, where the exact event moment is essential for result correctness.
  - In scenarios where events can arrive with significant delays, Ingestion Time may lead to incorrect results because late events will be processed with timestamps that do not reflect the real moment when they occurred.
